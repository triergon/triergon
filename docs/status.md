# Status

Everything is experimental. No module has yet passed every gate on its complete scope
(see [quality](quality.md)). The tables below give each area's state on the gate's two
targets: what is implemented, what is verified against the reference, its runtime and
memory, and what is open.

Runtime is the worst per-case upper bound of `T_triergon / T_reference`, graded against
the [ceiling](quality.md#gates), with how many cases pass and which is worst. Memory is
the largest per-case upper bounds of peak heap and of total resident peak RSS relative
to the reference, with how many cases are below it in both. Linux memory is measured
under the `linux-glibc-v4` observer, which counts `strdup` and `strndup`, admits
libstdc++'s operator `new` and `delete`, and counts read-only file mappings made during
the operation toward total RSS ([harness](quality.md#harness)). Every result comes from
the qualified host class, the AWS c6g.4xlarge (Graviton2); x86_64 has no performance runs
yet.

Containers, framing, subtitles and playback are measured against FFmpeg git revision
`d32b387f` on the 9.0 branch; codecs, decode sessions, capture and the playback MP4
terminal-media matrix against the FFmpeg 9.0.2 release; fonts against FreeType 2.15.0;
shaping against HarfBuzz 14.6.0 and FriBidi 1.0.17; rasterising, ASS parsing and ASS
rendering against libass 0.17.5 ([reference pins](quality.md#reference-and-corpus)).
Workers and references link under the [link policy](quality.md#measuring-performance)
`static-toolchain-runtime-trained-order-v1`: both sides link their toolchain runtime
support libraries from their static archives, and the media, playback and Matroska
playback workers, the framing worker on Linux AArch64 and the transport worker on ARMv7
link with the toolchain's `lld` in their trained orders, so their results reflect the
linker, the module order and the trained order together. The other workers keep the
default linker and module order, because a trained order made a row worse or would not
help.

## Reading the tables

The Runtime and Memory cells come from the evidence index:
[harness/status-rows.json](../harness/status-rows.json) names the gate results each row
shows and the run they come from, and `cargo xtask check-design` fails when a cell
differs from what those results measured; `cargo xtask status --write` writes them. A
rendered cell names its run's revision. The rows the file lists under `open_cells` keep
cells written by hand until `cargo xtask evidence measure` records what their results
measured ([evidence](quality.md#evidence)). Unless such a cell names another revision,
it comes from its table's full gate run at `5b8dd88f`, which includes the gate's
`codecs-audio` item, whose AAC, AC-3, E-AC-3 and DTS correctness lanes pass on both
targets. AAC in MOV uses the separate measurements of `codecs aac-access-units` at
that revision on one host per target. The gate schedules the same comparison and
collections as the `aac-access-units` item. A seek capability whose
cases belong to another row's feature names that row in both cells, and the feature's
row lists each capability's results. The Open column of the Linux AArch64 table says
what is not yet implemented, compared or within the gates, on both targets unless it
names one.

## Measured revisions

A rendered cell names the revision of the run it comes from, and
[harness/status-rows.json](../harness/status-rows.json) names the run's evidence sets. The
[evidence index](../harness/evidence/sets/) lists every archived set by its SHA-256 with the
gate results it holds, each with its gate target and what it measured, and every other
measurement the project cites, instruction counts and probes among them, with a reason
that says what the set holds. How each result changed over time is in the index and in
git.
